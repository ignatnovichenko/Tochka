# Что можно честно показать на защите

## Цель и реализованный пользовательский цикл

Локальный CLI-MVP сравнивает ответы моделей на пользовательских бизнесовых заданиях. Пользователь готовит JSONL задания и рубрики, выбирает solver/judge конфигурации, запускает `business run`, получает сырые ответы и отчёт HTML/CSV/JSON. Затем `business select` проверяет требования к качеству, coverage, ошибкам и времени и либо выбирает конфигурацию, либо явно возвращает отсутствие подходящих.

**Все содержательные оценки, включая численные, делает нейросеть-судья.** Программа проверяет структуру судейского ответа, диапазоны, полноту критериев и реальные цитаты, агрегирует нейронные оценки. Локальные contains/JSON и другие checks только диагностика, не решают качество вместо нейросети.

- Solver получает только task/context и выбранную инструкцию, не эталон/рубрику.
- Ошибки/недоступность judge дают unknown, не оценку0.
- Неизвестная цена не принимается за ноль. Несопоставимые границы времени не ранжируются как эквивалентные.
- Rawoutputs, hashes, точное покрытие, provenance и конфигурации сохранены.
- 166 unit tests прошли; fixtures явно отделены от настоящих ответов модели.

## Где есть реальная работа моделей

1. FinQA: 60 первоначальных попыток внешнего harness с проверенным импортом; дополнительно24 новых реальных native `run`→report→`compare`. Это **контрольное техническое исследование**, не целевой бизнесовый judge-only сценарий. На12 общих задачах0.5B0/12,7B3/12 для direct/CoT; DSL7B1/12. Малая dev-выборка, аннотационные оговорки, разные runtime/таймеры не допускают громких обобщений.
2. Отдельный CPU/T4 speedprobe на двух prompts одного задания: native decode5.096→27.149 ток/с; это не большой GPU quality-run и не контролируемый чистый эффект модели.
3. Business: первый настоящий local smoke потерял сессию после2 ответов solver и1 вердикта judge. Partial coverage1/2 честно сохранён. Судья7B оценил письмо0.625/failed, но его объяснение имело содержательные ошибки. Новый отдельный run02 завершён и независимо проверен: 2 solver + 2 judge calls, 1 валидное решение из 2. Числовой вердикт отклонён из-за лишнего пробела в точной цитате и остался null/unknown. Автовыбор вернул no_eligible_configuration. Это завершённый технический цикл, но не подтверждение качества судьи.
4. OpenCode: официальный CLI подключён, adapter и конфиги кандидата/судьи реализованы. Пробный запрос и один отдельно разрешённый authenticated контроль получили free429. **Успешного ответа OpenCode нет**. Offline parser tests не подменяют реальный успешный запрос. Paid fallback, обход API, смена профиля/сети отсутствуют.

## Что нельзя утверждать

- Нельзя называть судью сильным, откалиброванным или надёжным только по валидному JSON.
- Нельзя обещать гарантированный бизнес-SLA по двум синтетическим примерам или12 dev-вопросам.
- Нельзя говорить, что OpenCode уже успешно решил/оценил набор.
- В одном business run одна solver-модель с несколькими конфигурациями. Общий cross-model business selector пока не реализован.
- Нет веб-интерфейса, массового scheduler, промышленного sandbox, оплаты, скрытого auto-repair или бесшовного resume.
- Spreadsheet adapter проверяет готовые XLSX; он не является агентом, решающимExcel-задачи.

## Короткая демонстрация без внешних вызовов

```bash
python -m nir_eval doctor
python -m nir_eval business validate --cases data/business_cases.jsonl --rubrics data/business_rubrics.jsonl
python -m nir_eval business evaluate --cases data/business_cases.jsonl --rubrics data/business_rubrics.jsonl --responses data/business_responses_control.jsonl --judge-config configs/business_judge_disabled.json --output runs/my_disabled_demo
python -m unittest discover -s tests -v
```

Disabled-demo должен показать score/pass=null: это проверка честного поведения без подключённой модели. Для показа настоящих ответов открываются сохранённые reports и raw evidence, а не выдаётся повторное чтение файлов за новый inference.
