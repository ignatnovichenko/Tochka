# Автоматический выбор по сохранённым результатам

Это детерминированный выбор среди проверенных конфигураций на конкретной выборке, не LLM-судья, прогноз будущей точности или гарантия SLA. Команда не вызывает модели и не расходует API-бюджет.

Пользователь задаёт JSON-policy:

```json
{
  "min_accuracy": 0.20,
  "max_error_rate": 0.10,
  "max_mean_latency_seconds": 60,
  "quality_basis": "observed",
  "objective": "quality",
  "min_tasks": 12
}
```

Порог качества и допустимая доля ошибок — доли 0..1. `quality_basis=observed` использует измеренную accuracy; `wilson_lower` — нижнюю 95%-ю границу Wilson первого повтора каждой задачи. `max_error_rate` считает provider failures и ошибки разбора, не все неверные ответы; неверные ответы отдельно снижают accuracy.

`max_mean_latency_seconds` ограничивает среднее записанное время в его явно описанных границах, **не максимальную задержку каждого ответа**. `objective=quality` сначала выбирает качество, затем меньшую долю ошибок. `objective=latency` выбирает меньшую среднюю задержку только внутри одной сравнимой группы таймера/runtime. При полном равенстве возвращаются несколько кандидатов без произвольного победителя.

## Что проверяется

- Завершённые настоящие модельные прогоны, никаких oracle/replay.
- SHA manifests и records исходных прогонов относительно сохранённого comparison manifest.
- Полное покрытие IDs×protocols×repetitions, отсутствие дублей и неожиданного набора IDs.
- Одинаковые датасет, список задач, версия prompts и число повторов.
- Записи сравнения должны совпасть с проверенными источниками.
- Булевы correctness labels, ошибки в знаменателе, отсутствие конфликта «правильно и provider error».
- Отсутствующая/нечисловая задержка или неописанный scope не заменяются нулём.

Разные известные timer/runtime groups не ранжируются по времени и не подставляются под один временной лимит. При необходимости явно ограничьте `allowed_runs` списком имён сравнимых прогонов. Это выбор подмножества существующих данных, не переписывание измерений.

## Цена

`max_mean_cost_usd` требует полного покомпонентного значения `cost_usd` и явного provider-reported USD cost contract. Иначе кандидат получает `cost_unknown` и исключается при ценовом ограничении. Нулевые платные API-вызовы в локальном эксперименте **не превращаются в нулевую стоимость вычислений**. Без ценового ограничения поле остаётся null/unknown и не используется в ранжировании.

## Результаты

- `selected`: одна конфигурация прошла ограничения и правило ранжирования.
- `tied_configurations`: несколько равных кандидатов, победитель не выдуман.
- `no_eligible_configuration`: подходящих конфигураций нет; причины записаны для каждого кандидата.
- `incomparable_latency_scopes`: нельзя честно выбрать по разным таймерам/runtime; ограничьте список прогонов или используйте quality-only.
- Повреждённые hashes/coverage — ошибка входных доказательств, а не плохая оценка модели.

## Проверенные примеры

На сохранённых 60 FinQA benchmark-попытках:

1. Quality≥20%, error rate≤10%, средняя latency≤60 с → **7B/direct**: 25% observed accuracy, 1/12 parse error, 48.760 с среднее. Это пороги на данной выборке, не утверждение что 25% достаточно для реального применения.
2. Quality≥80% → **нет подходящей конфигурации**.
3. Quality≥20% и подтверждённая средняя цена≤$0 → **нет подходящей конфигурации**, потому что стоимость неизвестна.

Результаты сохранены в `runs/selection_examples/`. Предыдущее 0.5B измерение generate-only не выдаётся за эквивалент полного llama.cpp completion. Если временные границы неизвестны, такой кандидат не проходит временное ограничение.
