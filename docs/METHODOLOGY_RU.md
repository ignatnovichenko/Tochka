# Методика и границы выводов

## Исследовательская задача

Сравнить конфигурации языковой модели в воспроизводимой бизнес-задаче: ответить на вопрос по фрагментам финансового отчёта, правильно выбрать значения и выполнить вычисления. Отдельный XLSX-модуль подготовлен для последующей проверки изменения файлов, но сам не является офисным агентом.

## Пилот FinQA

Источник: публичный dev split FinQA, закреплённый commit и SHA-256 указаны в `data/finqa_dev.source.json`. Сортировка `SHA256('42:' + id)` выбирает первые 12 задач. Это детерминированная инженерная выборка, не балансировка по операциям. Выбор не менялся после просмотра модельных результатов. Test не использовался для подбора prompts; выполнение его gold-программ было только проверкой интерпретатора.

Первый эксперимент: одна модель Qwen2.5-0.5B-Instruct, direct и cot, greedy, один повтор на задачу. Порядок двух протоколов чередуется между задачами для ослабления простого эффекта порядка. Полный текст/таблица передаются без retrieval по gold и без усечения. ID не включён в model prompt. Model revision и toolchain закреплены.

CoT означает явное поле с краткими вычислениями, а не доступ к скрытому внутреннему reasoning модели. Протокол program реализован в MVP, но в первом и втором 24-попыточных direct/CoT пилотах не запускался.

## Проверка ответов

1. Один JSON object; допускается целиком обрамляющая JSON code fence. Не допускаются prose до/после, несколько объектов, NaN/Infinity и duplicate keys.
2. `answer` приводится к конечному числу или `yes`/`no`. Число строкой считается parseable, но не строгим соблюдением запрошенной схемы. Проценты явно делятся на 100; произвольная смена шкалы по эталону запрещена.
3. Численный результат округляется до пяти знаков и сравнивается с `qa.exe_ans`, как execution answer в официальном FinQA evaluator. Свободный человекочитаемый `qa.answer` не используется как gold.
4. Для program поддерживаются ровно операции FinQA, ссылки на уже вычисленные шаги и константы. Нет eval/exec или выполнения Python. Ограничены длина программы, число шагов и величина степени. Ошибки парсинга/деление на ноль/нечисловой результат считаются неверным ответом.
5. Доля точного совпадения токенов программы хранится отдельно. Она не равна официальному symbolic program accuracy.

Все выбранные ID × конфигурации × повторы входят в знаменатель, включая provider failures, невалидный JSON и пустые ответы. Частичный прогон нельзя импортировать как полный. Нет oracle fallback в измерениях модели; положительные/отрицательные контроли имеют отдельный provenance.

## Метрики

- Answer accuracy и число верных ответов.
- Provider errors и parse errors отдельно.
- Mean, median, p95 задержки; входные/выходные токены только если измерены.
- Стабильность валидного разобранного ответа между повторами, если повторы действительно были. Отсутствие повторов = unknown.
- Wilson 95% CI: один первый повтор на каждую задачу. Дополнительный percentile bootstrap усредняет повторения внутри задачи и пересэмплирует задачи, 2 000 итераций, seed=42. All-zero bootstrap вырождается; это не доказательство нулевой вероятности успеха. Поэтому главным в таблице показан Wilson.
- Pairwise task bootstrap работает по пересечению ID и одинаковому provenance. Эти интервалы не корректируются на множественные сравнения и не заменяют заранее заданный статистический план.
- Стоимость, TTFT, hosted-квантование и иные недоступные измерения остаются unknown. Нулевое число платных API вызовов не равно нулевой экономической стоимости CPU.

В исходном локальном пилоте latency охватывает `model.generate`; токенизация и загрузка модели не включены. В универсальном runner per-attempt latency включает адаптер целиком, без инициализации модели. В разных движках границы таймера и прогрев надо учитывать. Сравнивать скорость на разных железах как свойство модели нельзя.

## Проверка XLSX

Новый адаптер не повторяет небезопасное поведение исходного evaluator, который мог читать исходный файл вместо предсказания. Предсказания находятся в отдельном дереве; учтены фактическое число cases, лист answer_sheet, диапазоны и нестандартные имена исходных файлов. Проверяются аннотированные значения и типы в пределах документированного протокола; макросы/формулы не исполняются.

Формулы без доверенного пересчёта создают inconclusive; reference_error в эталоне также остаётся в знаменателе. `cached` режим доверяет сохранённым значениям, поэтому не годится как доказательство корректного вычисления без независимого пересчёта. В отчёте разделены наличие предсказаний, сравнение значений и покрытие решений.

## Основные угрозы валидности

Малая выборка; английский язык; старый публичный benchmark и неизвестная контаминация; узкая финансовая задача; ограниченная мощность маленькой модели; лимит генерации; разные режимы скорости; нет человеческой проверки свободных деловых текстов; нет запуска полноценных офисных действий. Нельзя переносить результат на качество «цифрового сотрудника», русский язык или все модели.

Если добавляется большая квантованная модель с другим движком, сравнение относится к целым конфигурациям. Оно не изолирует эффект числа параметров, квантования, backend или prompting отдельно.

## Следующий воспроизводимый этап

Зафиксировать модельные конфигурации и prompts на dev; заранее задать выборку и критерии; выполнить одинаковую матрицу на нескольких моделях; для stochastic режима провести независимые повторы; после фиксации протокола выполнить test. Добавить Office/XLSX agent только в изолированной среде с безопасными публичными данными и доверенным пересчётом. До этого слово «готовность» относится к MVP конвейера, а не к завершённому научному выводу.

## Неоднозначность исходной разметки

В FinQA встречаются вопросы с формулировкой percentage, где эталон выражен в долях, и другие, где он умножен на 100. Канонический exe_ans сохраняется без изменений; scorer не подбирает шкалу по эталону. Это ограничение сопоставимости прямых численных ответов, которое требует отдельного смыслового аудита. Можно заранее определить вторичную метрику единиц/масштаба или возвращать DSL, но нельзя изменить основной критерий после просмотра результатов и затем сравнивать его с исходным.

## Второй настоящий пилот и проверенное сравнение

Qwen2.5-7B-Instruct-GGUF, pinned revision `bb5d59e06d9551d752d08b292a50eb208b07ab1f`, Q4_K_M, llama-cpp-python 0.3.16, CPU 4 потока, n_ctx=4096. Тот же выбор 12 задач, те же prompts direct/cot, один greedy повтор, максимум 192 токена. Все 24 пар messages и rendered_prompt побайтно совпали с 0.5B. KV cache сбрасывался перед каждой измеренной генерацией. Отдельного прогрева не было; первые ответы не исключались.

Прямой и CoT протоколы получили по 3/12. Из этих верных ответов 2 общие и по 1 различаются. Между 0.5B и 7B для каждого протокола 3 discordant случая в пользу 7B; exact McNemar p=0.25. Это описательный результат на конкретных задачах, не доказательство общего превосходства.

Задержка 7B включает токенизацию prompt, prefill, генерацию и преобразование в строку, но не загрузку модели; 0.5B измерял только model.generate. Кроме размера меняются backend и dtype/квантование. Поэтому не вычисляйте причинный эффект размера или строгий speedup из этой таблицы. Исходные manifests сохраняют границы и окружение.

Независимый скрипт `scripts/audit_comparison.py` не использует основной scoring module: повторно читает 48 raw outputs, сопоставляет канонические scalars, проверяет hashes и парную идентичность prompts. Его результат находится в `runs/model_comparison/independent_audit.json`.

## Третий, дополнительный DSL-пилот

После просмотра двух исходных прогонов добавлена исследовательская конфигурация: та же 7B Q4_K_M, тот же runtime, 12 ID и лимит 192 токена, но protocol=program. Модель один раз генерирует FinQA DSL; локальный ограниченный калькулятор исполняет только валидный синтаксис. Нет итеративной обратной связи, repair или повторного выбора лучшей программы. 0.5B в этом протоколе не запускалась, поэтому матрица не полная.

12/12 попыток сохранены: 11 корректных JSON, 2 исполнимых DSL, 1 правильный ответ. 10 неисполняемых результатов входят в знаменатель. Неизменённый официальный FinQA evaluator дополнительно исполнил 2 валидные программы: оба числа совпали с ограниченным интерпретатором, official execution accuracy=1/12, official symbolic program accuracy=1/12. Это последняя отдельная метрика, а не переименование token exact match в основном runner.

Средняя задержка 59.120 с, медиана 57.337 с измеряют генерацию llama.cpp completion; вычисление калькулятора в этот таймер не включено. Результат показывает проблемы соблюдения DSL в этой конфигурации, но не доказывает бесполезность инструментов вообще: здесь не было работы агента с проверкой и исправлением ошибок. Все прежние результаты и caveats исходной разметки сохранены.

## CPU/GPU performance probe отдельно от качества

Приложение содержит два exact prompts одного FinQA case, исполненные на CPU и Colab Tesla T4 с одной pinned Qwen2.5-7B Q4_K_M и одинаковыми параметрами. Native counters сбрасывались перед каждым completion, отдельного прогрева не было. Для decode и prefill используются свои суммы токенов/времени; end-to-end completion wall time хранится отдельно.

Native decode CPU 5.09645 против GPU 27.14943 токенов/с, prefill 20.82502 против 720.20799. Выходы отличаются: 99 CPU и 100 GPU токенов. Поэтому одинаковые prompts/seed не создают идентичную траекторию CPU/CUDA вычислений. Это два запроса одной задачи, другие машина/CPU/CUDA backend, без повторений и CI скорости; результаты нельзя распространять на полный benchmark или обещать всем сессиям бесплатного Colab. Raw counters, hashes, native offload 29/29 log и исходники сохранены.

GPU-probe не заменяет CPU quality records и не добавляется к 60 основным benchmark-попыткам. Проверка `scripts/audit_speed_probe.py` не вызывает модель или сеть.
