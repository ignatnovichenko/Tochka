# Пользовательские бизнес-наборы: реализованный контракт

Текущий FinQA runner специализируется на финансовых вопросах. Произвольные пользовательские тексты не следует маскировать под FinQA: у них другая схема, критерии и способы проверки.

Business-модуль принимает следующий контракт:

- Case JSONL: `id`, `task`, `context`, `rubric_id`; необязательные `reference`, `checks`, `tags`.
- Rubric JSONL: `id`, список критериев `{id, description, weight}`, список критических ошибок, `pass_threshold`.
- Response JSONL: `id`, `response`, `model`, `configuration`, `repetition`, `status`.

Solver получает только `task` и `context`. Эталон, рубрика и проверки передаются только оценщику. Одинаковые ID/настройки/повторы должны полностью учитываться; отсутствие ответа — отдельный missing status, а не успешное прохождение.

Детерминированные проверки отделяются от LLM-судьи. Disabled/unavailable/error судьи не являются оценкой0 и не должны улучшать или ухудшать итоговый model score как будто это проверенный вердикт. Наличие структурированного JSON судьи само по себе не доказывает качество его оценки; для применения нужны контрольные примеры и человеческая проверка.

Реализованный CLI-цикл: business validate → business run (solver → сохранение raw responses/метаданных → нейросудья) → HTML/CSV/JSON → business select по judge coverage и ограничениям. Локальные checks только диагностические, все содержательные решения, включая числа, принадлежат judge. Unit tests и фактические model runs перечислены отдельно в README; реализация не равна доказанной надёжности судьи.

Локальный solver предпочтителен для чувствительных данных. Перед передачей внешнему provider необходимы разрешение на конкретные данные/получателя, проверка цены и условий. API keys задаются через окружение, не JSON или логи. Никаких ключей, регистрации или платного inference этот план не создаёт.
