# Бизнес-задачи: только модель-судья

Модуль `nir_eval.business` импортирует пользовательские текстовые задачи, контекст, эталоны, рубрики и ответы. **Качество каждого ответа, включая численные ответы, оценивает отдельная модель-судья.** Код проверяет только формат, целостность и полноту судейского решения, а затем считает взвешенную сводку выставленных судьёй баллов. Необязательные локальные checks служат диагностикой: они не меняют качество, pass/fail и не заменяют судью.

Без подключения судьи: `judge.status=unavailable`, `reason_code=judge_not_configured`, `score=null`, `passed=null`. Ошибка провайдера, исчерпание лимита, неверный JSON, таймаут или отсутствующий ответ также не превращаются в оценку качества 0. Только валидное решение подключённого судьи может дать passed/failed. Тестовые заглушки существуют исключительно в `tests/test_business.py` и не доступны через конфигурацию CLI.

## Быстрый технический контроль без модели

```bash
python -m nir_eval.business validate --cases data/business_cases.jsonl --rubrics data/business_rubrics.jsonl --responses data/business_responses_control.jsonl
python -m nir_eval.business evaluate --cases data/business_cases.jsonl --rubrics data/business_rubrics.jsonl --responses data/business_responses_control.jsonl --output runs/business_control
python -m unittest discover -s tests -p test_business.py -v
```

Демонстрационные ответы написаны вручную и явно помечены `handwritten-pipeline-control-not-model-inference`. Их наличие проверяет работу импорта и отчёта, а не качество LLM. Без судьи никакой процент успеха им не присваивается. HTML, JSON и CSV создаются в выходном каталоге, полные структурированные решения — в `records.jsonl`.

## Схема пользовательских данных

Один JSON-объект на строку UTF-8. Повторяющиеся ключи/ID, неизвестные поля, NaN/Infinity, лишние поля, неверные типы и ссылки на отсутствующие рубрики отвергаются.

Файл задач: обязательные `id`, `task`, `context` (строка), `rubric_id`; необязательные `reference` (строка), `tags` (список), `checks` (список диагностики). Task/context могут содержать произвольную задачу: письмо, резюме встречи, сравнение вариантов, финансовый расчёт. Эталон не обязателен, но полезен для численных задач. Для больших документов сначала подготовьте текст; PDF/XLSX не передаются как бинарные вложения этим модулем.

Файл рубрик: `id`, `criteria` (непустой список `{id, description, weight?}`), необязательные `description`, `critical_errors` (список `{id, description}`), `pass_threshold` в диапазоне 0–1, по умолчанию 0.75. Каждое число/единица/допуск, которые должен проверить судья, задаются в рубрике или эталоне. Пример `numeric_answer_v1` включён.

Файл ответов: `id`, `model`, `configuration`, `response`, необязательные `repetition` (целое ≥0), `status` (`ok`/`error`), `provenance`. При `error` текст ответа не используется. Для каждого обнаруженного сочетания модель/конфигурация/повтор проверяются все задачи; пропуски получают статус `missing`. Полностью отсутствующую конфигурацию из файла ответов вывести невозможно: её нужно явно создать в runner. Нельзя выбирать только успешные ответы.

Миграция существующих записей ядра:

```bash
python -m nir_eval.business import-records --input runs/solver/records.jsonl --output runs/business_responses.jsonl
```

Импорт переносит только `id`, `raw_output`, `model`, `config`, `repetition`, признак ошибки и provenance. Gold и диагностические результаты старого scorer не становятся оценкой бизнес-ответа.

## Подключение отдельного судьи

`configs/business_judge_local.example.json` — шаблон уже запущенного локального OpenAI-compatible сервера. Он не запускает и не скачивает модель. Укажите фактический model ID; ключ допускается только через переменную окружения `NIR_JUDGE_API_KEY` либо имя в `api_key_env`. Не вставляйте ключ в JSON, URL, командную строку, ответы или документы.

```bash
python -m nir_eval.business evaluate --cases data/business_cases.jsonl --rubrics data/business_rubrics.jsonl --responses runs/business_responses.jsonl --judge-config configs/business_judge_local.example.json --output runs/business_judged
```

Внешний HTTP заблокирован по умолчанию. Флаг `--allow-remote-judge` допускает только HTTPS и **не заменяет разрешение передавать данные, проверку условий, стоимости или платёжную авторизацию**. Нет автоматических повторов, перенаправлений, инструментов или платного fallback. `max_calls` ограничивает число попыток; превышение становится unavailable. Ответ сервера/ошибка не копируются в логи целиком; сохраняются только проверенная структура, ограниченные usage, хеши и безопасный код причины. Ответы, task/context и рубрики остаются в пользовательских входных файлах. Проверенные rationale/evidence в локальном журнале могут содержать цитаты из этих данных: обращаться с журналом нужно как с частными данными.

Адаптер `GenerationJudgeProvider(provider, model, parameters)` поддерживает существующий контракт `generate(messages, model, parameters, context) -> Generation`. Для собственного транспорта реализуйте `JudgeProvider` с полями `kind`, `model` и методом `judge(messages, case_id) -> JudgeReply(text, usage, metadata)`. Такой транспорт не должен передавать секреты в ответах/metadata и обязан соблюдать отдельное разрешение на внешние вызовы.

Конфигурация `generation-provider` подключает существующие локальные/command adapters ядра; любые команды должны быть доверенными и не содержать секреты в аргументах. Доступность модели и качество судьи — разные свойства. Работающий локальный 0.5B адаптер не делает эту модель достаточно сильным или валидированным судьёй.

### OpenCode Zen

Проверено по официальной документации: бесплатные модели требуют официального OpenCode CLI/SDK-host. Нельзя подключать их через произвольный прямой HTTP-клиент или имитировать заголовки официального клиента. Нейтральный интерфейс выше позволяет подключить официальный host отдельным адаптером. Этот модуль не утверждает, что такой вызов выполнен.

Кандидат для последующей проверки: `opencode/deepseek-v4.1-flash-free`; дополнительная калибровка — `opencode/longcat-2.5-free` или `opencode/glm-5.3-flash-free`. Доступность и фактический ID необходимо проверять текущим каталогом `opencode models`. Это рекомендации для проверки, не доказательство лучшего судьи. Muse Spark 1.3 относится к Meta, а не Mistral; проверенный каталог показывает paid `muse-spark-1.3`, поэтому её нельзя использовать как бесплатный fallback. Публичные синтетические данные, последовательный малый smoke, отсутствие платного fallback и проверка условий обязательны перед экспериментом. Разрешение на массовый benchmark из одной доступности CLI не следует.

Источники: https://opencode.ai/docs/console/api/inference/ ; https://opencode.ai/legal/terms-of-service ; https://artificialanalysis.ai/leaderboards/models . Проверено 10 ноября 2026 года; каталог меняется.

## Рубрика, решение и безопасность

Каждый критерий получает от судьи целый балл 0–4, краткое объяснение и доступные точные цитаты. Требуется ровно один результат для каждого критерия и каждого типа критической ошибки. Цитата должна буквально присутствовать в указанном источнике (candidate/context/task/reference). Выдуманные цитаты, дубли критериев, лишние поля, неверный ID, обрезанный ответ и нечисловые баллы дают `judge.status=error`, а не fail.

Код вычисляет взвешенную нормированную сводку `sum(score*weight)/(4*sum(weight))`. Pass определяется рубричным порогом и отсутствием критической ошибки, **обнаруженной судьёй**. Программная диагностика в это решение не входит. Это агрегирование судейских баллов, а не отдельная проверка правильности чисел кодом.

Reference, checks и rubric не передаются модели-исполнителю: `build_solver_messages` и `export-inputs` используют только task/context. Судья не получает название модели-кандидата. Task/context/reference/candidate передаются как недоверенные поля JSON в user-message; инструкция и рубрика изолированы в system-message. Произвольный код и пользовательские regex не выполняются. HTML экранируется, формулы CSV обезвреживаются. Это снижает риск prompt injection, но не является доказательством полной защиты: LLM может ошибаться и поддаваться атаке даже при корректной структуре.

## Исследовательские ограничения

Нужны отдельная калибровочная выборка, независимые человеческие оценки, проверка согласованности по критериям, повторные оценки и adversarial cases. Для сравнения сильных судей заранее фиксируются rubric, prompt, версия модели, параметры, набор и правила обработки пропусков. Ни валидный JSON, ни exact evidence match не доказывают правильность судьи. Тестовый HTTP-сервер ниже проверяет протокол, а не интеллектуальное качество.

Каждый запуск сохраняет хеши данных, кода, конфигурации, входа/выхода судьи, токены при наличии, задержку, статусы, проверенные критерии и критические ошибки. Запуск не перезаписывает существующий каталог; частично выполненный запуск имеет `state=running`, resume пока отсутствует. Повторы одной задачи зависимы: отчёт не заявляет доверительных интервалов для независимых попыток.
