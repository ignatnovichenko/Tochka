# SpreadsheetBench: безопасный локальный адаптер оценки XLSX

Рабочий компонент НИР, протокол `nir-spreadsheetbench-values-v1`. Это **оценщик готовых XLSX**, а не агент, который решает задачи, и не официальный leaderboard runner. Он не вызывает LLM, не отправляет данные в сеть, не запускает Python из ответов модели, макросы, Excel, LibreOffice или пересчёт формул.

## Что исправлено относительно сохранённого официального runner

В официальном `evaluation.py` на commit `49b73a94775fb489063f60ca1865e3a650079a79` путь `proc_path` указывает на исходный `input.xlsx`; строка с `outputs` закомментирована. Адаптер не импортирует и не запускает этот runner, читает только заданные `*_output.xlsx` из отдельного каталога.

Также адаптер:

- использует реальные номера случаев из объединения input/answer, а не цикл ровно из трёх элементов;
- учитывает `answer_sheet`, когда диапазон не содержит имя листа;
- обнаруживает пробел перед расширением в трёх реальных input-файлах, не переименовывая оригиналы;
- сохраняет пропавший input/answer как ошибку набора и оставляет случай в знаменателе;
- не принимает два пустых кеша формул за верный результат;
- возвращает явные статусы и первые пять несовпадений с координатами;
- ограничивает ZIP/XML и число проверяемых ячеек; не извлекает архивы на диск;
- запрещает выход пути через `..` и symlink, макросы, внешние workbook links, ActiveX, вложенные OLE, query tables, connections, DTD и XML entities.

Это защита в несколько слоёв, **не полноценная песочница ОС**. Произвольные внешние XLSX и тем более код агента следует запускать/разбирать в отдельном контейнере с лимитами памяти/CPU, без сети и секретов. Обычные гиперссылки не открываются.

## Установка и команды

Python 3.10+ и зафиксированный openpyxl 3.1.5:

```bash
cd mvp
python -m pip install '.[spreadsheet]'
python -m unittest discover -s tests -v

python -m nir_eval spreadsheet inventory \
  --dataset-root ../office_dataset/SpreadsheetBench/data/all_data_912_v0.1 \
  --out runs/spreadsheet_controls/inventory_912.json

python -m nir_eval spreadsheet evaluate \
  --dataset-root ../office_dataset/SpreadsheetBench/data/all_data_912_v0.1 \
  --predictions-dir ./predictions \
  --provenance model-inference \
  --formula-policy strict \
  --task-id 13-1 \
  --out reports/my_run.json
```

Установка не обязательна, если подходящий openpyxl уже есть. CLI возвращает 0, когда отчёт успешно создан, даже если все ответы неверные. Код 2 означает ошибку конфигурации/ввода. Статус выполнения CLI нельзя трактовать как прохождение бенчмарка.

`--provenance` обязателен: `control-not-llm` для контролей оценщика, `replay` для переоценки сохранённых результатов, `model-inference` для реально полученных ответов модели. Это заявление вызывающей стороны, не доказательство запуска модели. Для модели отдельно сохраняют provider/model/version, prompt hash, code hash, seed при поддержке, стоимость, токены, времена, ошибки и идентификатор запуска. Не указывайте `model-inference` для копии эталона.

## Контракт выходов агента

```text
predictions/
  13-1/
    1_13-1_output.xlsx
    2_13-1_output.xlsx
    3_13-1_output.xlsx
```

Разрешён только этот шаблон. Нет поиска «похожего» файла, fallback на input или автоматического использования reference. Каталог predictions должен лежать отдельно от корня benchmark: ни внутри, ни быть его родительским каталогом. Отчёт тоже сохраняется отдельно, не в dataset/predictions.

В модели оставляют только инструкцию, разрешённые метаданные и копию input-файла в её рабочем каталоге. **Не подключайте модели весь каталог бенчмарка:** там есть ответы. Private inventory и отчёт содержат пути к эталонам и значения для диагностики; они предназначены только для evaluator/orchestrator, не для solver prompt. Сам адаптер не создаёт такую изоляцию.

Python API:

```python
from nir_eval.spreadsheet import evaluate, inventory, Limits
manifest = inventory(dataset_root, task_ids=["13-1"])
report = evaluate(
    dataset_root,
    predictions_dir,
    provenance="replay",
    task_ids=["13-1"],
    formula_policy="strict",
    limits=Limits(max_cells=250_000),
    run_metadata={"run_id": "your-verified-run-id"},
)
```

Модуль переносимый: только stdlib + openpyxl; всегда передавайте `dataset_root` при включении в другой пакет. Значение по умолчанию рассчитано на текущую структуру соседних каталогов.

## Формулы и честные ограничения

`openpyxl` **не вычисляет формулы**. Читаются два представления файла: формулы и сохранённые значения.

- `strict` по умолчанию: формула в проверяемой ячейке предсказания даёт `inconclusive`, даже если кеш непустой. Свежесть кеша ничем не доказана.
- `cached`: только явный выбор пользователя/протокола. Непустой кеш используется для сравнения; отчёт предупреждает, что он может быть устаревшим или поддельным. Это не проверка эквивалентности формул.
- Формула без кеша в предсказании даёт `inconclusive`, в эталоне `reference_error`. Формула, реально возвращающая пустую строку, тоже может попасть сюда: адаптер намеренно консервативен.
- Кеши эталонных XLSX считаются доверенными как часть опубликованного набора. Правильность самих эталонов адаптер не доказывает.
- Вызов LibreOffice/Excel и его безопасность в этот компонент не входят. Для настоящих формульных задач нужен отдельно изолированный пересчёт, фиксированные engine/version/locale и сохранение исходного/пересчитанного SHA256. Даже после пересчёта выбор `cached` остаётся явным, а сведения об engine записываются в `run_metadata`.
- Константа, совпавшая с эталонным значением, считается верной. Наличие именно формулы, правильность алгоритма и способность переноса на новые данные не проверяются.

Проверяются **только значения в размеченных диапазонах**. Цвет, шрифты, диаграммы, макросы, скрытые листы, ширина колонок и изменения вне диапазона не входят в score. У некоторых задач цель визуальная, поэтому такой value-only score недостаточен. Для них нужен отдельный валидатор/ручная проверка.

Сохранены нормализации опубликованного comparator: числам и числовым строкам округление до двух знаков, датам до Excel-дня. Отсюда известные слабости: мелкие численные ошибки могут пройти, `True` совпадает с `1`, часть времени в датах теряется. Это не универсальная семантическая проверка Excel.

## Неоднозначная разметка и отличия протокола

Имена листов в 912 содержат непоследовательные внешние кавычки, которые снимаются при разборе. Полноширинный знак `：` в задаче `37456` нормализуется с предупреждением. Неоднозначные несколько `answer_sheet` для одного неквалифицированного диапазона не угадываются. Некорректный `BD2:308` у `73-45` не исправляется предположением и даёт `reference_error`.

Целые столбцы (`283-32`) проверяются до максимального использованного ряда **обоих** файлов, с явно записанной границей и лимитом ячеек. Удаление/появление ненулевых значений в хвосте не теряется. Поддерживаются A1 и A1:B2, целые столбцы и несколько диапазонов. Whole-row, named ranges и листы с запятой в имени данным форматом не поддержаны.

Из-за этих отличий результаты нельзя без оговорок сопоставлять с опубликованными leaderboard scores. Verified 400 имеет другой layout и в этой версии не поддерживается. Шесть XLSM в дополнительной папке `395-17` не относятся к 912 записям dataset.json и не включены в знаменатель.

## Статусы и знаменатели

- `pass`: все проверенные значения совпали по выбранному протоколу.
- `fail`: несовпадение, нет предсказания или нужного листа.
- `invalid_prediction`: архив/активное содержимое/формат предсказания отклонены.
- `inconclusive`: нельзя честно решить, например нет проверенного пересчёта формулы.
- `reference_error`: некорректна разметка, отсутствует эталон или его кеш.

`cases_total` включает **все случаи выбранных задач**, в том числе ошибки и пропавшие outputs. `case_pass_rate = pass / cases_total`. `task_soft_pass_rate` сначала усредняет успехи внутри каждой инструкции, затем между инструкциями. `task_hard_pass_rate` требует pass для всех случаев инструкции.

Неоценённые случаи не выбрасываются: если они есть, rate обозначен `lower_bound_unscored_as_not_passed`, а не точная оценка способностей модели. `coverage`/`decision_coverage` означает долю случаев с определённым решением (включая missing-output fail и invalid-prediction). Отдельно `prediction_coverage` показывает наличие файлов, `comparison_coverage` — долю реально сравненных значений. Так пустой каталог не выглядит заполненным прогоном, даже если все пропуски получили детерминированный fail.

## Проверки и артефакты

- `tests/test_adapter.py`: синтетические unit fixtures для самого оценщика, не дополнительные задания НИР.
- `scripts/sheet_smoke.py`: воспроизводимые контроли на первых N реальных инструкциях, строго `control-not-llm`.
- `runs/spreadsheet_controls/inventory_912.json`: 912 инструкций, 2729 полных input/answer пар. Распределение: 908×3, 1×2, 3×1; три input с пробелом перед `.xlsx`.
- `runs/verification.log`: фактический журнал unit-тестов.
- `runs/spreadsheet_controls/smoke_summary.json` и `smoke_*.json`: фактические результаты контролей; первая десятка не случайная и не репрезентативная.

Повторить smoke:

```bash
python scripts/sheet_smoke.py --tasks 10 --out-dir runs/sheet_smoke
```

`gold_copy_cached` просто копирует эталон, чтобы проверить работоспособность evaluator. `gold_copy_strict` демонстрирует консервативную обработку формул. `input_copy_noop` ничего не решает и копирует input. **Ни одно число этих контролей не является результатом LLM.** Генерация формул, вызов модели и полный прогон 912 инструкций здесь не проводились.

## Фактический smoke, 10 ноября 2026

На первых 10 инструкциях (30 случаев) обе копии эталона, `gold_copy_cached` и `gold_copy_strict`, дали 24 `pass` и 6 `reference_error`. У задач `19-7` и `23-28` есть пустые кеши формул в проверяемых ячейках. Это может быть корректным пустым результатом формулы, но без пересчёта его нельзя отличить от отсутствующего кеша. Поэтому адаптер не объявляет эти случаи успешными. Значение 24/30 — контроль инфраструктуры, **не точность модели**.
